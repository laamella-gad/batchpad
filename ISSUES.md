# Issues

Format: `- #N [type, priority] Title` with optional indented details.
Types: bug, feature, task. Priorities: high, normal, low.
Move an issue between sections to change its status. Never reuse a number; next free number: **#60**.

- #53 [feature, normal] Write C source for oscar64
  - Same content as the assembler output (#43): every labelled block becomes a `const` array (`charset_data`, `map_data`, `spriteset_data`, ...), the `colr_*`, `*_count`, `size_*` values become constants, names become a string table.
  - Tile events (#46): the jump table becomes an array of function pointers, `void (* const chartileset_events[])(void)`, one per tile, pointing at a function named after the tile (`chtl_<name>_event`, or `chtl_null_event`). Our output declares them; the user's code defines them. Optionally also write empty default functions.
  - Names must be valid C identifiers (as for #46).
  - Optionally a header (`.h`) with `extern` declarations and the `.c` with the data, so several files can include it.
  - Check what oscar64 offers for placing data at an address (needed for char sets and sprites in a VIC bank) and whether `#embed` of our raw binaries (#41) is the simpler route.
- #54 [feature, normal] Load address option for exports and imports
  - One option, shared by every binary export: write a 2-byte PRG load address (any value) or none. Default: none.
  - Imports: skip a load address when told to, or detect it from the size as CharPad/SpritePad do (#42); report the address found.
  - Could also feed the asm (#43) and C (#53) output, instead of CharPad's dummy `addr_* = $1000`.
- #55 [task, high] Design the command line arguments
  - List every import and export option (`docs/import-export.md`, #41-#54) and every setting in the CharPad and SpritePad files (display mode, colouring method, colours, tile system, flexi-grid, key map, overlay distances, animations, ...).
  - From that, come up with a consistent set of commands and arguments: input/output files, what to export, cell width (8/12/16 bit), load address, assembler or C dialect, label names, sub-maps, overrides of project settings.

- #56 [feature, low] Read and write SEUCK `.A` sprite files
  - `$42 $00`, then 127 sprites of 64 bytes (8130 bytes); the 64th byte is `000M CCCC`. Layout in `docs/import-export.md`, conversions in `docs/spritepad.md` (SpritePad 1.8 and Pro agree).
  - Export: colour + `$10` if multicolour, pad to 127 sprites with zero blocks, refuse more than 127. Import: bit 4 becomes multicolour (bit 7), bits 5-7 dropped.
  - Also as an attribute style for raw sprite export/import (#41, #42): SpritePad, SEUCK or Ignore (`$8c` on import, 0 on export).
- #57 [feature, low] Read and write SEUCK `.B` background files
  - 9596 bytes: `$42 $00`; map 8 x 512 bytes, bottom to top; 128 tile colours; 128 unused bytes; 128 tiles of 5 x 5; 254 chars; `$3f`, 9 x `$ff`. Layout in `docs/import-export.md`.
  - Only for a project with exactly those sizes and per-tile colouring, as CharPad does; report what doesn't fit.
  - CharPad 1.7 also wrote backgrounds for the "sideways SEUCK mod" (819 x 5 map), same file layout with the map bytes reordered; see docs/import-export.md. The file doesn't say which kind it is, so this needs an option.
- #59 [task, normal] Find out how CharPad stores ECM chars 64 and up
  - ECM shows only 64 shapes; CharPad Pro treats chars 64-255 as copies of chars 0-63 in the other three background colour banks, each with its own colour and material (3.88 help, "ECM Mode Tips"). Pixel edits and transforms on char 64+ go to char & 63.
  - Open: does a saved CTM hold the same 8 bytes for char n and n & 63, or the char's own (possibly stale) data? What happens with more than 256 chars? Matters for char set exports and for what our readers and writers should do with ECM projects.
  - Check with a CharPad Pro 3.88 ECM project of more than 64 chars, saved after editing a char in the first bank, and in the decompiled code (`Form_CPV_CharEdit`, the set operations).
